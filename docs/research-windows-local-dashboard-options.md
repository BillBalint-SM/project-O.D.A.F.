# Windows-local dashboard delivery options

**Research date:** 2026-09-27
**Question:** [Issue #28](https://github.com/BillBalint-SM/project-O.D.A.F./issues/28) asks which maintained Windows-local UI and packaging options can present ODAF fleet/status while invoking the same PowerShell 5.1/Hyper-V command surface.
**Source policy:** Primary sources only: ODAF's accepted project documents and official Microsoft/.NET/PowerShell/Pester documentation. Product capabilities below are documented facts; the recommendation is an engineering judgment for ODAF's stated v1 scope.

## Recommendation

For the smallest first dashboard, use a **PowerShell 5.1 desktop script with a native Windows Forms UI**, calling the existing ODAF command/status functions directly. Keep all lifecycle and assignment rules in the shared command layer; the UI renders its machine-readable status and calls the same operations as the CLI. This fits the accepted Windows host boundary, where Windows PowerShell 5.1 and Hyper-V cmdlets own fleet control and a host-local dashboard is required ([ADR 0001](adr/0001-control-plane-and-runtime.md), [ADR 0004](adr/0004-fleet-lifecycle-and-validation.md)). Windows PowerShell 5.1 is installed by default on supported Windows client versions, and its Desktop edition is built on .NET Framework; Windows Forms' .NET Framework implementation is distributed with .NET Framework ([PowerShell 5.1](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_windows_powershell_5.1?view=powershell-5.1), [Windows Forms overview](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/overview/)).

Choose a **loopback web UI** only if browser layout, responsive presentation, or richer web UI automation is important enough to justify a separate local server and its deployment/runtime contract. For a maintained server, use ASP.NET Core/Kestrel and invoke the same PowerShell 5.1 command surface through a narrow, fixed operation boundary; do not duplicate fleet logic in the web app. Kestrel documents `localhost` loopback defaults and supports explicit endpoint configuration ([Kestrel endpoints](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0)).

## Comparison

| Option | Smallest viable shape | Local-only security | Installation and maintenance | Testability |
|---|---|---|---|---|
| **Native WinForms (recommended v1)** | One Windows PowerShell 5.1 entry point, `System.Windows.Forms`, and the existing ODAF command/status functions in the same user process. No HTTP endpoint or browser bridge. | No dashboard web listener to expose. Keep UI actions constrained to named ODAF operations; show explicit confirmation for consequential actions and preserve the operator's existing Windows permissions. | Uses the built-in Windows PowerShell and .NET Framework WinForms stack on the supported Windows host. The .NET Framework WinForms implementation is Windows-only and treated as an OS component. | Keep the command/status contract as the primary test seam. Pester supports Windows PowerShell 5.1 and mocks dependencies, so lifecycle decisions can be tested independently of the form ([Pester installation and compatibility](https://pester.dev/docs/introduction/installation), [mocking](https://pester.dev/docs/usage/mocking)). UI interaction still needs a small manual or UI-automation smoke pass; do not make it the only validation route. |
| **Loopback browser UI with ASP.NET Core/Kestrel** | Local web process serves the UI and a narrow API. The API invokes fixed PowerShell 5.1 operations, preferably with structured arguments/results rather than interpolated command text. | Bind explicitly to loopback only; reject unexpected Host/Origin values, allow only required routes/methods, and require an unguessable per-launch token for mutating calls. Do not expose wildcard or LAN endpoints or rely on CORS as authorization. Kestrel's documented `localhost` binding uses IPv4 and IPv6 loopback; endpoint configuration is controllable ([Kestrel endpoints](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0)). | Adds a separately built .NET app and the choice of framework-dependent versus self-contained deployment; self-contained deployment ships its runtime, while framework-dependent deployment expects a shared runtime ([.NET deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/)). It is a more maintainable web server basis than `HttpListener`. | The API can be tested as an HTTP boundary, while the shared PowerShell behavior remains covered by Pester. Browser-level testing adds another test/runtime component and is not required to validate fleet decisions. |
| **Loopback browser UI with `HttpListener`** | A PowerShell 5.1 process serves static files and a small HTTP API using .NET Framework's `System.Net.HttpListener`. It avoids a separately installed web runtime. | The listener runs with the process's permissions. Prefix selection matters: Microsoft warns against top-level `*` and `+` wildcard bindings because they can expose security vulnerabilities; use an explicit loopback host and apply the same request protections as above ([HttpListener class](https://learn.microsoft.com/en-us/dotnet/api/system.net.httplistener?view=netframework-4.8.1)). | Small initial package, but Microsoft says `HttpListener` receives limited servicing and is not recommended for new development; Microsoft recommends ASP.NET Core instead ([HttpListener remarks](https://learn.microsoft.com/en-us/dotnet/api/system.net.httplistener?view=netframework-4.8.1)). This is a prototype option, not the maintained web choice. | HTTP-level checks are possible, but the custom routing, request parsing, and lifecycle code become ODAF-maintained responsibilities. Pester can still test command behavior; it does not remove the server's maintenance burden. |

## Security and deployment findings

- A local UI is not a reason to widen the authority of the process. Route actions through the existing validated ODAF operations, avoid arbitrary PowerShell text, retain operator approval for consequential operations, and expose stale/unreachable status as unknown per [ADR 0001](adr/0001-control-plane-and-runtime.md).
- For a web option, a loopback listener is a network boundary choice, not an authorization policy. Use an explicit loopback endpoint, a per-run secret for state-changing requests, strict request-origin/host checks, and no wildcard binding. These are implementation requirements for the proposed local API, not capabilities provided automatically by binding to `localhost`.
- Do not change the machine's PowerShell execution policy as an installer step. Microsoft describes execution policy as defense in depth, not a security boundary; policy can also be set by Group Policy and override local preferences ([PowerShell execution policies](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1)). Package/distribute the script under the repository's chosen trust/signing approach and report a blocked policy clearly.
- Do not install a Windows service for the first dashboard. The accepted requirement is an operator-facing local UI on the Windows host, and dashboard closure must not stop guest work ([ADR 0001](adr/0001-control-plane-and-runtime.md)). A foreground user process keeps UI lifetime and visible operator consent straightforward.

## Decision boundary

Use native WinForms for v1: it minimizes runtime and process boundaries while meeting the stated single-operator, Windows-host requirements. Keep the display layer thin and the CLI/status contract authoritative. Reconsider ASP.NET Core/Kestrel if the pilot demonstrates that browser-based rendering or browser automation has enough value to justify a second runtime and a secured loopback API. Skip `HttpListener` for new production work because its upstream documentation explicitly advises against new development. No option changes the accepted host/guest authority model, and this comparison does not implement W01 or select concrete screen behavior.
