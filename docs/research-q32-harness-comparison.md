# Issue #32: harness capabilities for three non-implementation roles

- Research date: 2026-09-27
- Scope: Compare Pi, Codex CLI and Hermes Agent for research/specification, architecture/planning, and independent test/review on an Ubuntu guest.
- Source policy: Current first-party project documentation, repositories and ODAF decisions only. Capability statements below describe published behavior, not a guest pilot or performance measurement.
- Status: Evidence and operational considerations; no final profile or harness selection.

## Evidence by harness

### Pi

Pi's first-party README describes a terminal agent with interactive and automated print, JSON and RPC modes; it documents npm installation on Linux and a Node.js 22.19+ requirement. Its usage guide documents automatic session persistence, resuming with `pi --continue`, selecting another session, and forking a prior conversation. These modes map cleanly to one-off source synthesis, iterative specification work and repeatable review prompts, but the suitability assessment is an inference rather than a product guarantee. ([Pi README](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md), [Pi usage guide](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/usage.md), [Pi sessions](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sessions.md))

Pi supports configurable tools, skills and context files. Its own security statement says it has no built-in permission system restricting filesystem, process, network or credential access; it inherits the launching user's authority and recommends containerization or another sandbox for stronger boundaries. Thus, Pi's extension flexibility is not itself least-privilege enforcement. For research/specification and independent review, a read-only filesystem/container boundary would need to be provided outside the harness if writing is not allowed. ([Pi CLI usage](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/usage.md), [Pi security and containerization](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/containerization.md))

### Codex CLI

OpenAI documents a standalone macOS/Linux CLI installation, interactive repository work, and `codex exec` for repeatable workflows. The command reference documents session continuation by ID or most-recent selection for both interactive and exec runs. Skills and repository instructions can supply research methods, architecture templates or review criteria without requiring a separate harness-specific agent process. ([Codex CLI guide](https://developers.openai.com/codex/cli/), [CLI command reference](https://developers.openai.com/codex/cli/reference), [Codex AGENTS.md](https://developers.openai.com/codex/guides/agents-md), [Codex skills](https://developers.openai.com/codex/skills))

Codex permission settings are explicit: documented modes include read-only, workspace-write and full access; approval policies include on-request and never. The docs describe workspace-write/on-request as a bounded local-work pattern, with approval requested for actions outside configured limits. This gives a documented mechanism for separating read-only investigation/review from planning that may create artifacts, subject to actual configuration and host enforcement. Session resume is documented, but process survival after a guest reboot, Herdr disconnect semantics and unattended approval handling must be validated in ODAF's deployment path. ([Codex sandbox and approvals](https://developers.openai.com/codex/security), [Codex configuration basics](https://developers.openai.com/codex/config-basic), [CLI command reference](https://developers.openai.com/codex/cli/reference))

### Hermes Agent

Hermes documents Tier 1 support for Linux/WSL2, tested against the latest Ubuntu, plus installation and a `hermes doctor` health check. Its CLI supports session continuation, structured output, skill preloading and toolset selection; its TUI shares the same runtime and saved sessions. This provides first-party readiness signals and more than one invocation surface, though “latest Ubuntu” does not prove compatibility with ODAF's specific image or installed dependencies. ([Platform support](https://hermes-agent.nousresearch.com/docs/getting-started/platform-support), [installation](https://hermes-agent.nousresearch.com/docs/getting-started/installation/), [CLI reference](https://hermes-agent.nousresearch.com/docs/reference/cli-commands), [TUI](https://hermes-agent.nousresearch.com/docs/user-guide/tui))

Hermes toolsets group terminal, file, browser, web, memory, delegation and other capabilities; skills are installable knowledge bundles. Dangerous terminal commands can prompt and be approved once, for a session, always, or denied. Its docs distinguish command approval from isolation: the default local backend runs on the same OS account with no containment, profiles do not sandbox, and configured Docker or other sandbox backends provide the execution boundary. Its broad built-in feature set may reduce external integration work for research and review, but it also makes an explicit minimal toolset and health policy important. ([Tools and toolsets](https://hermes-agent.nousresearch.com/docs/user-guide/features/tools), [skills](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills), [security](https://hermes-agent.nousresearch.com/docs/user-guide/security), [profiles](https://hermes-agent.nousresearch.com/docs/user-guide/profiles/))

## Role-level comparison (inference)

- **Research/specification:** All three expose a terminal workflow and resumable sessions. Pi emphasizes a small extensible loop; Codex exposes both interactive and scriptable modes; Hermes bundles web-oriented, terminal and skill features. Whether those bundled capabilities improve source quality or citation completeness must be assessed using the same evidence-based task brief.
- **Architecture/planning:** Each can receive repository context and produce structured text. Codex and Hermes explicitly expose skill/context mechanisms and operational controls; Pi provides a deliberately extensible foundation. Nothing in vendor documentation proves one will produce more implementable plans for ODAF.
- **Independent test/review:** Codex offers an explicit read-only mode; Pi can be run with an external read-only boundary but has no native permission system; Hermes has command approvals and container backends, but its default local backend is not isolated. Review independence also requires a separate work item/context and no write access to the maker's workspace; a second model process alone does not prove independence.

These are capability-based inferences, not profile choices. ODAF's accepted policy requires a separate test/review agent to check maker evidence, and places consequential acceptance with the operator. The harness can execute and report; it does not own ODAF assignment, fleet readiness, work-item state or final approval. Herdr owns terminal/pane lifecycle in the first interactive pilot; a harness session's resume feature does not supersede that process boundary. ([ADR 0001](adr/0001-control-plane-and-runtime.md), [ADR 0006](adr/0006-component-authority-and-optional-orchestration.md), [ADR 0007](adr/0007-work-routing-and-evidence.md), [authority matrix](agent-stack-and-authority.md))

## Readiness and unresolved compatibility

Documentation makes each candidate plausible to investigate on Linux, but does not establish that any candidate is ready in an ODAF guest. Before relying on one, verify the exact guest OS/architecture and system libraries; pinned install/version/update path; provider authentication without embedding credentials; required network endpoints; tool availability and permission behavior; resource use within the guest budget; `doctor`/smoke status; session persistence across process restart and VM restart; and the Herdr-owned launch, reconnect and stop behavior. For review, verify that source access is read-only and that artifacts reach ODAF without giving the harness publication authority.

No numerical CPU/RAM, cost, accuracy or elapsed-time comparison is available from the sources reviewed. Those belong to a future controlled comparison, with identical task briefs, acceptance criteria, permitted tools, provider/model budget and independent operator evaluation. This note does not choose a final profile or run that comparison.

## ODAF boundary

The ODAF control plane owns fleet and assignment records; the guest supervisor prepares the selected profile and reports readiness; the selected harness owns its inner model/tool loop and session; Herdr owns the initial interactive terminal/pane lifecycle; the operator owns consequential approval. Harness selection must not silently add permissions, authorize publishing, replace readiness reporting, or make an agent's self-report equivalent to accepted review evidence.
